## 적용 내용

- Q5는 메뉴를 방문 전 정하기 / 도착 후 정하기, Q6는 일정 변경이 몇 주의 흐름에 미칠 영향 / 오늘 바로 조정할 부분을 대비한다. helper도 의미에 맞게 수정했다. id·순서·축·옵션 value/code·총 20문항·축당 5문항·다수 집계는 유지했다.
- 개인 결과의 각 축 선택 예시 바로 뒤에 ‘이번 선택을 돌아보면’ 문단을 넣었다. 실제 Q번호와 선택지 원문만 인용한다. 혼합 답변은 두 방향의 예시, 5:0은 실제 선택 하나와 열린 질문을 표시한다. 코드 전용·답변 확인 실패에는 개인 문단이 없다.
- 판단 기록 가이드의 해당 단락 마지막 두 문장은 승인 인용문으로 교체했다. 승인 인용문은 실제 두 문장이며 이전 보고서의 ‘세 문장’ 설명은 정정했다.
- 결과 URL을 향하는 홈·가이드 링크 네 곳에 `prefetch={false}`를 지정했다. 제목을 나중에 강제로 덮어쓰거나 지연 시간을 늘리는 수정은 하지 않았다.
- 수동 관리 문항 사양 표를 새 문안에 맞췄다. 가이드의 가상 전체 원문·실제 사례는 현재 `QUESTIONS`에서 생성되어 함께 반영된다.

## 문항 버전과 이전 기록 보존

문항 의미가 바뀌므로 기존 answers 비트를 새 문구의 실제 선택으로 다시 표시하면 부정확하다. 다음 범위를 함께 적용했다.

| 경로 | 동작 |
|---|---|
| 새 테스트 | 계산·개인 결과까지 `v=2` 전달, 새 Q5·Q6 인용 |
| 버전 없는 기존 개인 링크·명시적 `v=1` | 기존 Q5·Q6 원문으로 실제 선택 재현 |
| 알 수 없거나 중복된 v | 답변 확인 실패의 코드 기본 설명. 개인 근거 없음 |
| 결과 공유 링크 | 기존처럼 code만 포함. answers·v와 개인 회고 제외 |
| 임시 저장 | `gaemitype.answers.v2` 사용. 구 키를 새 문항 답변으로 자동 복원하지 않음 |
| 처음부터·다시 테스트 | 현재 키와 구 키 `gaemitype.answers`를 함께 초기화. 다른 앱 키는 보존 |

이전 20문항의 모든 필드가 기준 HEAD 원본과 같고, 현재의 나머지 18문항도 변경되지 않았음을 직접 대조했다. 이후 문항 의미를 다시 바꿀 때도 버전을 올리고 과거 문항 원문을 보존해야 한다. 사용자 모집은 이번 구현·검증의 선행 조건으로 두지 않았다.

## 결과 제목의 원인과 검증

앱의 `generateMetadata`는 현재 code를 읽고 있었지만, 사전 로딩된 동일 경로의 다른 query metadata가 재사용되는 Next의 알려진 문제와 증상이 일치했다. 기술 검토자는 설치된 Next 16.3.3의 head cache 저장 경로에서도 query가 빠지는 동일 패턴을 확인했다. [upstream 이슈](https://github.com/vercel/next.js/issues/97657), [수정 PR](https://github.com/vercel/next.js/pull/97729).

의존성을 바꾸는 대신 오염원이 되는 결과 링크의 자동 prefetch를 끄는 최소 회피책을 적용했다. 이 선택은 해당 링크의 자동 사전 로딩 이점을 포기하지만, 실제 클릭·결과 URL 접근은 유지한다.

| 검사 | 수정 전 | 수정 후 |
|---|---|---|
| 랜딩→20문항→ATRC 결과 | h1은 상황가늠형, DOM title·OG·canonical은 ALRD | ATRC 본문·title·OG·code 전용 canonical 일치 |
| ALRD 맛보기 실제 클릭→다시 테스트→ATRC 완주 | 최종 후보에서 별도 확인 | 새로고침 없이 ATRC 일치, `v=2` 전달 |
| 가이드에서 ALRC·ALRD 클릭 및 뒤로가기 | 해당 경로 추가 확인 | 전환 완료 후 각 타입의 title·OG·canonical 일치 |
| 직접 진입·새로고침 | 서버 직접 응답은 기존에도 정상 | 현재 타입에 맞는 메타 유지 |

수정 전 로컬 운영 빌드에서도 같은 실패를 직접 확인했다. 기준 빌드의 사이트 URL 기본값은 localhost:3000이었고, 최종 로컬 빌드·실행에는 해당 프로세스에만 `NEXT_PUBLIC_SITE_URL=http://127.0.0.1:3010`을 지정했다. 운영 환경변수나 env 파일은 바꾸지 않았다.

## 실제 브라우저 검증

- 랜딩 결과 맛보기 ALRD를 실제 클릭한 뒤 새 20문항을 완주했다. 새 Q5·Q6가 보이고 ATRC 개인 결과에 v2가 전달됐다. 모든 축에 실제 선택을 연결한 회고 네 문단이 표시됐다.
- 360×800에서 혼합, 한쪽 응답, 코드 전용, 잘못된 answers, 구버전, 알 수 없는 버전을 확인했다. 개인은 네 회고, 공유·오류는 회고와 개인 선택 사례 0개였다.
- 360px의 문서 너비는 345px이며 회고 영역은 clientWidth와 scrollWidth가 모두 269px였다. 캡처로 줄바꿈·카드 배치도 확인했다. 1440px에서는 문서 너비 1425px, 가로 넘침 없음.
- 구버전 개인 결과 Q6는 ‘구독하고 그 채널의 다른 영상을 섭렵한다’를 그대로 표시했다. 새 한쪽 응답 Q6는 새 문안을 표시했다.
- 개인 ATRC에서 결과 링크를 실제 복사해 `http://127.0.0.1:3010/result?code=ATRC`만 나오는 것을 확인했다. 공유 문구에도 타입 문구만 있었다.
- 결과→읽기 가이드 이동, 가이드의 타입 링크 전환, 판단 기록 가이드의 보류 안내 표시를 확인했다. 검증 탭 error 로그 0개.

클립보드는 첫 검사에서 비동기 쓰기 완료 전에 읽어 빈 값이었다. 복사 완료 버튼 상태를 기다리는 검사로 보정해 실제 생성 URL을 확인했다. 메타데이터도 전환 직후 빈 값을 읽은 시점과 title locator 대기 실패가 있어, 페이지 전환 완료(networkidle) 후 실제 DOM title·OG·canonical을 함께 대조했다. 제품 코드를 이 검사 보정 때문에 추가로 바꾸지는 않았다.

메인은 URL 재현성과 실제 선택의 정직성을 우선해 구버전 개인 결과를 코드 전용으로 축소하는 대신 당시 원문을 보존했다. Q5/Q6 및 helper 외 문항은 확대 수정하지 않았다. 최종 리뷰의 구 키 정리는 수정 전 실패를 확인한 일회성 검사로 재현한 뒤 고치고 전체 테스트를 다시 통과했다. 미처리 코드 리뷰 항목은 없다.

최종 리뷰가 실행하지 않은 브라우저 메타데이터 검증은 메인이 위 경로로 확인했다. 기존 dirty README·이전 기록은 범위 밖 보존 대상이라는 판단을 유지했다. 기존 문서를 reset·stash·삭제하지 않았다.
