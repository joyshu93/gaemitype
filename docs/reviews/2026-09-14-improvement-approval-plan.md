## 3. P1 — 4축과 16타입을 같은 의미로 정리

**위치:** 모든 /result?code=코드의 이름·별칭·대표 설명·축 카드·특징·습관·주의점·공유 문구, 관련 기존 랜딩 맛보기·소개·가이드. 아래 타입별 링크는 해당 변경의 위치다.

**근거:** O의 F01·F02, B2–B5·B9·B10, C1·C6. 속도·우열·성공·낙관성·추진력 등 문항이 직접 묻지 않은 특성이 본문에 추가되고, D/C 차이가 탐색 폭 차이로 번진다.

**사용자 영향 해석:** 선호 요약을 능력 검사로 받아들이거나 같은 페이지의 축·이름·본문 중 무엇을 믿을지 헷갈릴 수 있다. 이는 실제 사용자 반응의 측정이나 계산 오류 판정이 아니다.

**적용 범위:** 16타입, 개인 응답·코드 전용·답변 확인 실패의 모든 정상 타입 화면. 기존 코드·이미지 경로는 유지한다.

**확인 기준:** 아래 8극·16타입·인접 쌍 규칙에 따라 모든 문장을 설명할 수 있고, 미측정 능력·우열·성과·정확한 투자 시점 판단 문장이 남지 않는다. 기존 그림을 포함한 완성 화면과 복사·메타데이터도 함께 검수한다.

### 3.1 8개 극 설명: 현재 → 대체

축명·코드·극명은 유지한다. A/P는 정하는 시점, L/T는 살피는 시간 범위, R/I는 먼저 참조하는 단서, D/C는 납득하는 설명 방식을 구분하는 편집 기준이다. 현 질문이 네 개념을 완벽히 분리한다는 주장은 아니다.

| 극 | 현재 설명 | 대체 설명 |
|---|---|---|
| A 준비형 | 움직이기 전에 기준과 흐름을 먼저 정리해두면 더 편안한 쪽이에요. | 시작하기 전에 순서나 확인할 내용을 미리 정리해두는 편이에요. |
| P 현장형 | 상황을 보면서 그때그때 더 맞는 쪽으로 조정하는 편이에요. | 상황을 직접 보거나 해보면서 필요한 순서와 방법을 정해가는 편이에요. |
| L 흐름형 | 짧은 흔들림보다 조금 더 긴 흐름과 방향을 보는 편이에요. | 당장의 변화보다 시간이 지나도 이어갈 방향과 만족을 먼저 살펴보는 편이에요. |

### 3.4 본문 전체를 닫는 편집 규칙

대표 문장만 고치고 기존 장점·습관·주의점을 남기지 않는다. **현재의 “이런 점이 잘 보여요”와 “이런 모습이 자주 보여요”를 “이 타입을 장면으로 보면” 한 구획으로 합친다.** 기존 “이럴 때 흔들릴 수 있어요”는 “돌아볼 질문”으로 바꾼다. 결과 안의 중복을 줄이는 범위이며 별도 기능을 추가하지 않는다.

공통 안내는 “아래는 같은 타입에 공통으로 제공되는 설명이에요. 장면은 타입의 뜻을 풀어 쓴 예시이며, 실제 선택 기록은 아니에요.”로 고정한다. 응답 모드에서는 이어 “이번 답변의 차이는 위의 선택 횟수와 사례에서 확인할 수 있어요.”를 붙인다. 공유에서는 이 추가 문장을 붙이지 않는다.

각 타입의 **설명 장면은 아래 AP·LT 조합 1개 + RI·DC 조합 1개**, 돌아볼 질문은 **해당 AP 1개 + DC 1개**로 확정한다. 이 조합은 문서의 편집 규칙이다. 구현에서 실시간 문장 생성이나 AI 추론을 도입할 필요 없이 16개 정적 데이터에 펼쳐 쓴다. 16개 모두의 본문이 아래 규칙으로 완전히 지정되며 기존 능력·약점 문장을 덧붙이지 않는다.

| 조합 | “이 타입을 장면으로 보면” 대체 문안 |
|---|---|
| AL | 나들이를 떠나기 전에 살펴볼 순서를 정리하고, 하루 동안 이어질 동선을 생각해보는 모습이에요. |
| AT | 나들이를 떠나기 전에 살펴볼 순서를 정리하고, 지금 바꿔야 할 일정이 있는지 보는 모습이에요. |
| PL | 나들이 현장에서 상황을 보며 순서를 정하고, 하루 동안 이어질 동선을 생각해보는 모습이에요. |
| PT | 나들이 현장에서 상황을 보며 순서를 정하고, 지금 바꿔야 할 일정이 있는지 보는 모습이에요. |
| RD | 새 앱을 살펴볼 때 원래 중요했던 조건을 떠올리고, 기능과 이용 조건이 항목별로 정리된 설명에서 납득하는 모습이에요. |
| RC | 새 앱을 살펴볼 때 원래 중요했던 조건을 떠올리고, 기능들이 이어지는 전체 사용 장면에서 납득하는 모습이에요. |
| ID | 새 앱을 살펴볼 때 새로 소개된 정보에 눈길을 두고, 기능과 이용 조건이 항목별로 정리된 설명에서 납득하는 모습이에요. |
| IC | 새 앱을 살펴볼 때 새로 소개된 정보에 눈길을 두고, 기능들이 이어지는 전체 사용 장면에서 납득하는 모습이에요. |

| 극 | “돌아볼 질문” 대체 문안 |
|---|---|
| A | 미리 정해둔 것과 현장에서 달리 정한 것은 무엇이었나요? |
| P | 상황을 보며 정한 것과 미리 정해두었던 것은 무엇이었나요? |
| D | 납득에 도움이 된 구체적인 내용은 무엇이었나요? 전체 장면도 함께 떠올려볼까요? |
| C | 납득에 도움이 된 전체 장면은 무엇이었나요? 그 안의 구체적인 내용도 함께 떠올려볼까요? |

예를 들어 PLID의 본문은 PL+ID, 질문은 P+D다. PLIC는 PL+IC, 질문은 P+C다. 이 차이에 낙관·고집·탐색 폭·추진력 차이를 추가하지 않는다. 질문은 사용자에게 회상을 권할 뿐 그 경험이 실제 있었다고 주장하지 않는다. “돌아볼 질문” 아래에는 **“실제로 떠오르는 장면만 생각해봐도 괜찮아요. 두 방식의 경험이 모두 있어야 하는 것은 아니에요.”**를 공통 안내로 둔다.

아래는 삭제될 현재 표현과 새 본문이 제공할 의미를 연결한 표다. 같은 문장을 새 본문에 중복 삽입하는 추가 작업 목록은 아니다.

| 현재 위치·문구 | 대체 의미·문안 | 제거하는 추론 |
|---|---|---|
| ALRD 특징 “생각보다 쉽게 휩쓸리지 않아요” | “원래 중요했던 조건을 떠올리고…”(RD) | 흔들리지 않는 능력 |
| ALRD 주의 “준비가 길어져 타이밍을 놓칠 때” | “미리 정해둔 것과 현장에서 달리 정한 것은…”(A) | 기회 상실·타이밍 실패 단정 |
| ALRC 특징 “균형이 좋은 편” | “원래 중요했던 조건…전체 사용 장면”(RC) | 우수한 균형 감각 |
| ALID 습관 “여러 방향을 같이” / ALIC “한 방향을 깊게” | ID는 항목별 설명, IC는 전체 사용 장면 | D/C에 없는 탐색 폭 차이 |

| ATRD “반응 속도가 좋은 편” | AT+RD의 설명 장면 | 반응 속도 능력 |
| ATRC “타이밍을 잘 살피는”, “좋은 순간” | AT+RC의 설명 장면 | 적절한 시점 식별 능력 |
| ATID “남들이 지나친”, “다른 가능성을 잘 봐요” | AT+ID의 새 정보·근거 확인 | 역발상·비교 우위 |
| ATIC “남들보다 빨리”, “속도감 있는 상황에 강해요” | AT+IC의 미리 정리·현재 장면 | 속도 등급·포착 성공 |
| PLRD “크게 흔들리지 않고 길게 가요” | PL+RD의 상황 속 결정·이어지는 동선 | 흔들림 회피 보장 |
| PLRC “집중력이 높아져요”, “힘이 좋은 편” | PL+RC의 설명 장면 | 집중력·추진 능력 |
| PLID “낙관”, “감으로 이어갈”, “리듬을 느끼며 가요” | PL+ID, 질문 P+D | 낙관·타인 추종·근거 생략 단정 |
| PLIC “추진력이 강해요”, “브레이크가 약해질” | PL+IC, 질문 P+C | 강한 추진·통제 부족 단정 |
| PTRD “빠르게 보고 빠르게 맞추는 힘” | PT+RD의 상황 속 기준·항목 확인 | 빠르고 정확한 대응 능력 |
| PTRC “속도감 있는 흐름에 강해요” | PT+RC의 현재 조건·전체 장면 | 승부·성과 능력 |
| PTID “유연해서 답답함이 적어요” | PT+ID의 새 정보·조건 확인 | 유연성 우위·감정 추정 |
| PTIC “기회 포착 속도가 아주 빨라요”, “남들이 보기 전” | PT+IC의 현장 결정·새 정보 | 가장 빠른 감지·투자 기회 포착 |

### 3.5 한 글자만 다른 타입을 실제 문구로 비교

현재 문구는 O와 C의 발췌다. 아래 대체 비교는 공통 장면을 두고 달라지는 축만 보여준다. 사용자에게 일어난 일이나 차순위 타입 추천이 아니다. 비교용 새 화면은 만들지 않는다.

| 달라진 축 | 타입 1 현재 | 타입 2 현재 | 타입 1 대체 | 타입 2 대체 |
|---|---|---|---|---|
| A/P | ALRD “시작 전에 기준을 정리” | PLRD “바로 뛰어들기보다 흐름이 이어지는지 먼저” | 나들이를 떠나기 전에 살펴볼 순서를 정리해요. | 나들이 현장에서 상황을 보며 순서를 정해요. |
| L/T | ALRD “짧은 소음보다 큰 흐름을 더 오래” | ATRD “움직임은 빠르지만”, “반응 속도가 좋은” | 루틴을 시작할 순서를 미리 정하고, 며칠에 걸친 흐름을 살펴봐요. | 루틴을 시작할 순서를 미리 정하고, 오늘 바꿀 부분을 살펴봐요. |
| R/I | ALRD “먼저 체크할 기준” | ALID “흥미로운 게 보이면 관련된 조각들을 오래 모아” | 새 앱에서 원래 중요했던 조건을 먼저 떠올려요. | 새 앱에서 새로 소개된 정보에 먼저 눈길이 가요. |
| D/C | ALRD “기준부터”, “납득하면 오래” | ALRC “자기 기준”, “전체 흐름을 차분히” | 기능과 이용 조건이 항목별로 정리되면 납득이 가요. | 기능들이 이어지는 전체 사용 장면이 그려지면 납득이 가요. |
| D/C | ALID “여러 방향을 같이” | ALIC “여럿을 비교하기보다 한 방향을 깊게” | 새로 소개된 정보에서 구체적인 항목을 하나씩 확인해요. | 새로 소개된 정보에서 전체 사용 장면을 떠올려요. |
| A/P | ATIC “몸이 먼저”, “남들보다 빨리” | PTIC “가장 민감”, “남들이 보기 전” | 새 일정 후보가 보이면 움직이기 전에 살펴볼 순서를 정리해요. | 새 일정 후보가 보이면 현장 상황을 보며 순서를 정해요. |
| D/C | PLID “분위기”, “감으로” | PLIC “확신”, “추진력이 강해요” | 상황을 보며 정하되, 구체적인 근거가 정리되면 납득이 가요. | 상황을 보며 정하되, 전체 맥락이 그려지면 납득이 가요. |

공통 세 축은 3.3·3.4의 동일한 문안으로 보존한다. 예를 들어 ALID/ALIC는 AL과 I가 같고, ATIC/PTIC는 T와 IC가 같다. A도 빨리 행동할 수 있고 D도 확인을 생략할 수 있으므로 현재 조합을 논리적으로 불가능하다고 판정하지 않는다. 문제는 현 질문으로 그 속도·생략 습관을 대표 특성으로 추가할 근거가 없다는 점이다.

| 기록 가이드 | 세 줄 기록과 완성 예시 유지. 공유 정보 범위 문장만 필요 시 **“결과 링크 복사로 만든 링크에는 타입 코드만 담겨요. 답변 내용과 선택 횟수는 포함되지 않아요.”**로 통일 |

원래 ‘공유 문구 복사’에 URL이 없는 동작은 이번에 바꾸지 않는다. ‘결과 링크 복사’의 코드 전용 URL 생성 동작도 유지한다. 위 안내는 **복사 버튼이 만든 링크**에 한정한다. 주소창의 answers 포함 URL을 복사하면 답변이 포함된다는 기존 동작을 숨기거나 “모든 링크에는 답변이 없다”고 설명하지 않는다.

**확인 기준:** 16개 메타데이터와 복사 결과에서 공식 이름·뜻이 일치하고 과장 문구가 없다. 외부 메신저의 캐시는 별도 수동 검증으로 다룬다. 소개·가이드에 제작 주체·검증 이력·정확도를 새로 만들어 넣지 않는다. 새 가이드를 추가하지 않는다.

## 4. P2 — 응답이 없는 결과에는 분포를 만들지 않기

**위치:** /result 상단 정보 상태, 네 축 카드, 기본 설명 안내. 코드 전용 링크는 3.2의 16개 URL 전체가 대상이다.

**근거:** B1·B8에서 응답 부재 안내와 끝점 막대 공존. C3의 0/100 위치 합성. B9의 가이드는 횟수가 강도가 아니라고 설명한다.

**사용자 영향 해석:** 공유 수신자는 없는 5:0 분포나 매우 강한 성향을 추측할 수 있다. 회색 트랙·중간점도 분포를 암시하므로 해결책이 아니다.

### 4.1 입력·표시 상태 계약

브라우저나 방문자의 신원을 판정하는 규칙이 아니다. ‘응답 결과’란 **현재 URL에 들어 있는 선택값으로 재현한 결과**다. 유효 응답 URL을 다른 사람이 열어도 같은 답변이 표시되는 기존 성질은 유지한다.

| 입력 상태 | 화면 제목·안내 | 횟수·막대·실제 선택 예시 |
|---|---|---|
| 등록된 코드 + 정확히 20자리 0/1 + 현재 집계 코드 일치 | **이번 답변으로 나온 결과** / “이 링크의 답변에서 각 축마다 더 많이 고른 쪽을 모았어요. 같은 타입이어도 선택 횟수와 답변 내용은 다를 수 있어요.” | 실제 값만 표시. P3 규칙 적용 |
| 등록된 코드, answers 매개변수 자체 없음 | **타입 설명만 담긴 링크** / “이 링크에는 타입 코드만 있어요. 답변 내용과 선택 횟수는 포함되지 않아요.” | 전부 없음 |
| 등록된 코드 + answers는 있지만 빈 값·19/21자리 등 잘못된 길이·0/1 이외 문자·집계 코드 불일치 | **타입 설명만 보여드려요** / “답변 정보를 확인할 수 없어 타입 코드의 기본 설명만 보여드려요. 선택 횟수와 답변 사례는 표시하지 않아요.” | 전부 없음. 일부 유효 답변만 추려 개인 근거를 만들지 않음 |
| 잘못된 코드·누락된 코드 | 기존 결과 없음 안내와 다시 시작 동선 유지 | 다른 코드를 추정해 표시하지 않음 |

중복 매개변수는 다음으로 확정한다. **code가 두 개 이상이면 결과 없음**, **단일 유효 code에 answers가 두 개 이상이면 답변 확인 실패**로 처리한다. 동일한 값이 반복되어도 중복을 인정하지 않는다. source는 값·중복 여부와 관계없이 판정에서 무시한다. source=answers만 붙여도 응답 결과가 되지 않으며, source가 빠지거나 다른 값이어도 유효 code·answers라면 같은 응답 결과다. 그 밖의 무관한 매개변수는 응답 근거를 만드는 데 쓰지 않는다.

**입력 경계 보강의 제한:** 단일 유효 code·단일 answers, 정확한 20자리 0/1, 집계 코드 일치 조건만 개인 표시 입구에서 확인한다. 점수 합산·다수결·질문 매핑은 변경하지 않는다. localStorage 스키마, 미완료 계산 흐름, 재시작 기능 전체를 고치는 작업은 포함하지 않는다. 이 경계를 지나지 못하면 화면에서 개인 선택 근거를 만들지 않는다.

### 4.2 표시 전후

| 영역 | 현재 | 승인안 |
|---|---|---|
| 상단 보조 라벨 | 데스크톱에서 공유도 “내 판단 습관 요약” | 응답: “이번 답변 요약”, 코드 전용·확인 실패: “타입 기본 설명”. 모바일에서도 정보 상태 본문은 항상 보임 |
| 정보 순서 | 타입명·별칭 → 큰 캐릭터 → 대표 설명 → 모드 안내 | **타입명·별칭 → 대표 설명 → 상태 안내 → 기존 캐릭터 → 4축 → 타입 공통 설명 → 참고·가이드·공유** |
| 코드 전용 축 | 선택된 글자, 양끝 이름, 연속 막대·끝점, “세부 응답 강도 대신…” | **축 제목 / 선택된 글자·이름 / 그 뜻**만 표시. 네 카드의 반복 응답 부재 문구 제거 |
| 답변 확인 실패 축 | 일반 공유 결과로 내려감 | 코드 전용과 같은 수치 없는 축 카드 + 상단의 별도 실패 안내 |
| 비어 있는 분포 | 끝점 합성 | **아무 수치·트랙·점도 만들지 않음.** 0:0, 5:0, 50:50, 50%, 중간점, 빈 막대, 회색 척도, 개인 카드 높이를 맞추는 빈 분포 영역 모두 사용하지 않음 |

공유 카드 승인 예시:

> 판단 준비 방식  
> **A · 준비형**  
> 시작하기 전에 순서나 확인할 내용을 미리 정리해두는 쪽을 뜻해요.

이는 축의 선택된 범주를 설명하며 응답자의 선택 횟수나 강도는 말하지 않는다. 상단의 응답 부재 안내는 한 번 명확히 보여준다. 색·비활성 표시만으로 상태를 전달하지 않는다.

**적용 경로:** 외부 공유 수신, 직접 코드 URL 입력, 개인 응답 방문 후 같은 브라우저의 코드 URL 재열기, 다른 저장 응답이 있는 브라우저, 답변 확인 실패. 결과에 localStorage를 보충하거나 코드에서 응답을 역생성하지 않는다.

**확인 기준:** 같은 ALRD의 3:2·5:0·코드 전용을 나란히 열면 앞의 둘만 실제 횟수와 근거가 다르고, 마지막은 DOM·접근성 트리·시각 화면 어디에도 개인 분포가 없다. 정상 기존 링크는 같은 코드로 열리고, 모드 안내는 캐릭터를 지나기 전에 읽을 수 있다.

## 5. P3 — 실제 선택과 축 해석 연결

**위치:** [ALRD 혼합 응답](https://gaemitype.vercel.app/result?code=ALRD&answers=01010010100101001010&source=answers)을 포함한 유효 응답 결과의 4축 카드. 타입 공통 설명보다 먼저 제공한다.

**근거:** B6·B7에서 숫자는 있지만 개별 선택 인용은 없고 본문은 동일. C1·C2·C5에서 문항과 선택 코드를 연결할 입력은 있으나 UI까지 전달되지 않는다.

**사용자 영향 해석:** 반대 방향을 골랐던 장면이 사라져 한쪽 성격으로 단정된다고 느낄 수 있다. 개수만으로는 어느 답변이 어느 축에 반영됐는지 알기 어렵다.

### 5.1 실제 근거 선택 규칙

1. P2의 유효성 확인을 통과한 **동일한 AnswerState**로 집계와 예시를 만든다. QUESTIONS의 id·axis·options[selected].code·label을 사용한다. 배열 위치만 보고 축을 따로 하드코딩하거나 결과 코드에서 답변을 추정하지 않는다.
2. 축마다 **왼쪽 방향의 실제 선택 중 문항 순서상 첫 1개**, **오른쪽 방향의 실제 선택 중 첫 1개**를 표시한다. 표시는 고정된 AP/LT/RI/DC 축 순서, 각 축의 좌→우 순서다. 우세한 쪽을 앞으로 재정렬하지 않는다.
3. 3:2·4:1은 실제 양쪽 사례가 하나씩, 5:0은 한쪽 사례 하나만 나온다. 최대 8개다. 반대 사례가 없으면 빈 카드·가상 선택·비선택 원문을 채우지 않는다.
4. 제목은 **“이 축에 반영된 선택 예시”**. 질문 번호·질문 원문·고른 선택지 원문·반영된 글자를 보여준다. 선택지 내용을 감정·동기·생활 경험으로 재작성하지 않는다. 이번 기본안은 문항·선택지 원문을 그대로 사용하며 의미를 축약하지 않는다.
5. 예시 두 개가 집계의 전부처럼 보이지 않도록 **“총 5개 답변 중, 각 방향에서 먼저 나온 선택을 하나씩 보여드려요.”**를 공통 설명으로 둔다. ‘중요한 답’, ‘성격을 결정한 답’이라고 부르지 않는다. 실제 집계에는 해당 축 5개 모두가 같은 1회로 반영된다.
6. 카드 내용은 접힘 없이 보인다. 횟수·해설·선택 예시를 핵심으로 두고 모바일에서 사례를 좌우로 나누지 않는다. 질문과 선택지는 줄임표·행 제한 없이 읽을 수 있게 한다.

### 5.2 축별 횟수 해설 — 완성 문안

횟수는 **이름 + 선택 n개**로 쓴다. 기존 “응답 기준 요약: A 3 / P 2”보다 이름과 수를 먼저 읽을 수 있게 한다. A/P를 예로 들며 다른 축도 실제 이름을 대입한다.

| 실제 집계 | 해설 |
|---|---|
| A3/P2 | **“이번 다섯 문항에서는 준비형 선택 3개, 현장형 선택 2개였어요. 두 방식을 모두 골랐고 준비형 선택이 하나 더 많았어요.”** |
| A2/P3 | “이번 다섯 문항에서는 준비형 선택 2개, 현장형 선택 3개였어요. 두 방식을 모두 골랐고 현장형 선택이 하나 더 많았어요.” |
| A4/P1 | “이번 다섯 문항에서는 준비형 선택 4개, 현장형 선택 1개였어요. 준비형을 더 많이 골랐고, 현장형을 고른 답변도 하나 있었어요.” |
| A1/P4 | “이번 다섯 문항에서는 준비형 선택 1개, 현장형 선택 4개였어요. 현장형을 더 많이 골랐고, 준비형을 고른 답변도 하나 있었어요.” |
| A5/P0 | **“이번 다섯 문항에서는 준비형 선택 5개, 현장형 선택 0개였어요. 이번에는 모두 준비형 쪽을 골랐지만, 다른 상황에서도 늘 같은 방식을 고른다는 뜻은 아니에요.”** |
| A0/P5 | “이번 다섯 문항에서는 준비형 선택 0개, 현장형 선택 5개였어요. 이번에는 모두 현장형 쪽을 골랐지만, 다른 상황에서도 늘 같은 방식을 고른다는 뜻은 아니에요.” |

4축 시작부 공통 문구: **“숫자는 이번 답변에서 각 방향을 고른 횟수예요. 성격의 강도, 검사 정확도, 투자 능력을 뜻하지 않아요.”**

기존 개인 막대는 실제 선택 비율의 보조 표시로만 유지할 수 있다. 기본 승인안에서는 위치 계산을 바꾸지 않고 **횟수 텍스트 아래**에 둔다. 이름은 “선택 횟수 분포”, 새로운 백분율 숫자·점수·성격 강도 라벨은 추가하지 않는다. 접근성에서는 실제 횟수 텍스트가 의미를 전하고 장식용 점이 별도 능력 값으로 읽히지 않아야 한다. 실제 5:0의 0은 유효한 관찰 횟수이며 공유의 가짜 대체값 0과 다르다.

### 5.3 기존 혼합 시나리오를 실제 매핑에 연결한 예

아래는 O E08–E10의 검증용 선택열 **01010010100101001010**과 C1의 실제 매핑을 대조한 결과다. B6에서 네 축 3:2를 재확인했다. 사용자 자신의 응답이라고 주장하지 않는다.

| 축·집계 | 5개 모두의 집계 내역 | 규칙상 화면에 표시할 실제 선택 예시 |
|---|---|---|
| AP: A3/P2 | A: Q1·Q3·Q5 / P: Q2·Q4 | **Q1 → A:** “후기와 메뉴를 먼저 검색해본다” / **Q2 → P:** “일단 출발하고 가는 길에 하나씩 정한다” |
| LT: L3/T2 | L: Q6·Q8·Q10 / T: Q7·Q9 | **Q6 → L:** “구독하고 그 채널의 다른 영상을 섭렵한다” / **Q7 → T:** “지금 크게 세일하는지 확인한다” |
| RI: R3/I2 | R: Q11·Q13·Q15 / I: Q12·Q14 | **Q11 → R:** “내가 원래 보던 기준부터 먼저 떠올린다” / **Q12 → I:** “지금 눈에 띄는 새로운 변수다” |
| DC: D3/C2 | D: Q16·Q18·Q20 / C: Q17·Q19 | **Q16 → D:** “왜 좋은지 근거를 차근차근 말해주는 설명” / **Q17 → C:** “전체 흐름부터 잡아야 감이 온다” |

AP 카드의 완성 예시:

> **판단 준비 방식 · A 준비형**  
> 준비형 선택 **3개** · 현장형 선택 **2개**  
> 이번 다섯 문항에서는 두 방식을 모두 골랐고 준비형 선택이 하나 더 많았어요.
>
> **이 축에 반영된 선택 예시**  
> Q1. 친구가 맛집을 추천했어요. 오늘 저녁에 바로 가볼 수 있다면, 당신은 먼저 어떻게 하나요?  
> 고른 답변: **“후기와 메뉴를 먼저 검색해본다” → A 준비형**  
> Q2. 주말에 짧게 놀러 가기로 했어요. 출발 전 당신 모습에 더 가까운 쪽은?  
> 고른 답변: **“일단 출발하고 가는 길에 하나씩 정한다” → P 현장형**

실제 00000000000000000000 결과에서는 AP에 Q1→A, LT에 Q6→L, RI에 Q11→R, DC에 Q16→D 하나씩만 표시한다. 같은 ALRD라서 이름·캐릭터·기본 설명은 같지만 횟수·해설·선택 사례 수는 다르다.

Q7의 할인 선택을 T로 합산하는 것은 현재 매핑 사실이다. 이 예시에서 “투자 타이밍을 잘 잡아서”라는 이유를 만들어 설명하지 않는다. Q5·Q7 등의 문항 적합성은 S1에 남으며 실제 답변을 보여준 것만으로 문제가 해결되었다고 하지 않는다.

**적용 범위:** 모든 유효 응답 URL, 새로고침, 다른 브라우저에서 유효 응답 URL 열기, 이전 답변 수정 후 결과, 가이드에서 뒤로가기. 코드 전용·답변 확인 실패에는 이 구획 자체를 렌더링하지 않는다.

**확인 기준:** 각 축 총계 5, 실제 집계와 다수 글자 일치, 모든 인용이 현재 URL에서 실제 고른 원문, 반대 선택이 있으면 예시 포함, 없으면 예시 없음. 서로 다른 답변이 같은 코드가 되더라도 예시는 각 URL에 따라 달라진다.

## 6. 구현 후 검증 기준

아래는 **다음 구현 라운드가 충족해야 할 기준**이다. 이번에 수정된 제품을 테스트했다는 기록이 아니다. 결과 계산·매핑·모드 분기를 우선 검증한다.

### 입력·응답·공유 경로

초과 길이 거부로 바뀌는 것은 21자리 이상 비정상 URL이다. 정상 20자리 기존 URL과 16개 코드 전용 URL은 계속 재현된다. 이 호환 범위는 승인 전에 숨기지 않는다.

### 모바일·데스크톱·접근성

- **390×844 / 1440×900:** 타입명·대표 뜻·상태 안내가 캐릭터보다 먼저 온다. 일반 글자 크기 첫 화면에서 상태 제목과 안내를 읽을 수 있게 상단 여백을 조정한다. 4축 전부를 첫 화면에 넣는 것은 필수조건이 아니다.
- **360×640:** 본문·긴 원문·URL에서 가로 넘침, 글자 겹침, 잘린 답변이 없어야 한다. 상태가 캐릭터보다 먼저 나오며 짧은 세로 스크롤은 허용한다.
- 모바일은 카드 한 열, 축 내부 예시도 한 열. 긴 답변은 자연스럽게 줄바꿈하고 줄임표로 선택의 뜻을 감추지 않는다. 데스크톱은 기존 두 열 배치를 유지할 수 있다.
- 세로 길이를 줄이려고 근거를 기본 접힘으로 숨기지 않는다. 최대 축당 두 사례와 P1의 중복 본문 축소로 길이를 관리한다.
- 키보드·스크린리더로 상태·축명·선택 횟수·질문 번호·인용 순서를 읽을 수 있어야 한다. 색이나 점 위치만으로 뜻을 전달하지 않는다. 공유에서는 숨겨진 분포 값도 읽히지 않아야 한다.
- 200% 글자 확대 시 고정 높이로 원문이 잘리지 않아야 한다. iPhone/Safari·Android/Chrome 실물에서 이전 응답 수정·마지막 선택·복사·재열기를 확인한다.
- 바뀐 문안과 기존 그림을 나란히 보고 능력 등급으로 해석될 표현이 남았는지 검수한다. PTRC·PLIC·PTIC는 그림과 이름의 조합을 집중 확인한다.

### 16타입 및 모든 한 글자 차이 검수 목록

16타입 모두에서 이름·별칭·두 대표 문장·두 설명 장면·두 질문·축·그림·복사·메타데이터를 대조한다. 고유한 한 글자 차이 쌍은 총 32개다. 아래 8쌍씩 네 묶음을 빠짐없이 검사한다.

| 달라진 축 | 검수할 쌍 |
|---|---|
| A/P | ALRD–PLRD, ALRC–PLRC, ALID–PLID, ALIC–PLIC, ATRD–PTRD, ATRC–PTRC, ATID–PTID, ATIC–PTIC |
| L/T | ALRD–ATRD, ALRC–ATRC, ALID–ATID, ALIC–ATIC, PLRD–PTRD, PLRC–PTRC, PLID–PTID, PLIC–PTIC |
| R/I | ALRD–ALID, ALRC–ALIC, ATRD–ATID, ATRC–ATIC, PLRD–PLID, PLRC–PLIC, PTRD–PTID, PTRC–PTIC |
| D/C | ALRD–ALRC, ALID–ALIC, ATRD–ATRC, ATID–ATIC, PLRD–PLRC, PLID–PLIC, PTRD–PTRC, PTID–PTIC |

통과 기준은 같은 세 축의 뜻이 뒤집히지 않고 달라진 축만 설명 차이를 만드는 것이다. 별칭과 그림이 다르다는 이유로 추가 성격·능력 차이를 붙이지 않는다.

구현 후에는 순수 함수에서 실제 예시 추출·입력 모드·경계 및 위 집계를 검증하고, 화면에서는 공유 분포/근거 DOM 부재와 개인 원문 표시를 검증한다. 기존 npm test는 광고·파비콘·가이드 위주이므로 그것만으로 결과 검증을 대신하지 않는다. 승인 후 변경 범위에 맞는 테스트와 npm run lint, npm test, npm run build 결과를 기록한다. 이번 문서 라운드에서는 제품 빌드·테스트를 실행하거나 배포 적합성을 판정하지 않는다.

## 7. 역할별 검토와 메인 통합 결정

AGENTS.md에 따라 PM·Technical Architect·QA를 먼저 병렬 호출했다. 이후 Type System 검토와 UX/IA·Brand/Copy 검토를 병렬로 진행했다. 도구의 에이전트 수 제한으로 QA 검토자가 UX/IA, Technical Architect 검토자가 Brand/Copy 역할로 전환해 원본 관찰을 다시 검토했다. 따라서 여섯 명의 독립 조사자가 아니라 **여섯 역할의 AI 검토**다. 서로 다른 역할의 결론을 정답으로 따르지 않도록 지시했고, 각 역할이 근거와 해석을 분리했다. 브라우저 재확인은 메인이 수행했다.

| 역할 | 근거에 따른 검토 요약 | 메인 결정 |
|---|---|---|
| PM | F01–F04 세 건으로 닫기. 실제 선택 예시는 방향별 첫 사례, 그림 전체 재제작·기능 확장 제외 | P1–P3 채택. 관련 기존 설명 동기화만 포함 |
| Technical Architect | URL 응답이 개인 근거 출처. 공유 도메인에는 점수 없고 UI가 끝점 합성. 21자리 초과 허용 경계 발견 | URL·저장 구조 유지. 수치 없는 모드와 정확한 20자리 표시 조건 명시 |
| QA | 가짜 중간값도 불가. source·저장 답변으로 개인화 금지. 손상 응답 안내, OG 잔여 카피와 경계 검증 필요 | fallback 문구와 전 출력 경로 검수 포함. 실제 0과 가짜 공유 0 구별 |
| UX/IA | 대표 뜻·정보 상태를 그림 앞으로. 실제 선택 예시 접힘 없이, 최대 두 개. 기본 타입 설명과 이번 답변 구분 | 상단 순서 최소 이동, 기존 이미지 크기 유지, 원문 표시 채택 |
| Type System | AP/RI·LT/DC를 구분하는 8극과 네 축 조합의 16요약 제시. Q5 등 문항 한계는 남음 | 8극·16요약의 의미 기준 채택. 문항·매핑은 S1로 분리 |
| Brand/Copy | 캐릭터의 재미 유지, 미측정 의미가 이름에 붙은 7개만 개명. 반복 특징보다 장면·돌아볼 질문 권고 | 7개 이름 후보를 하나씩 선택해 승인안에 명시. 두 반복 본문을 두 장면으로 합침 |

### 충돌 지점과 판단 이유

1. **이름 보존 vs 의미 교정:** PM은 필요성이 남는 이름만 최소 교체, Type System은 일부 이름 후보, Brand는 7개 교체를 권고했다. 메인은 기존 코드·그림은 유지하면서 **ATRC·ATID·ATIC·PLID·PLIC·PTRC·PTIC의 이름만 변경**하는 안을 선택했다. 능력·우열을 걷는 제품 원칙을 우선하고, 16개 전면 개명보다 좁게 제한했다.
2. **축 문장 완전성 vs 읽는 재미:** Type System의 동일 골격은 검수에 유리하지만 Brand는 반복 구획의 단조로움을 지적했다. 대표 두 문장은 명확하게 유지하고, 기존 특징·습관은 구체적인 두 장면으로 합쳤다. 캐릭터·별칭이 재미를 맡고 문장이 측정 범위를 넘지 않게 한다.
3. **이미지 중심 인상 vs 상태 이해:** UX는 상태를 그림 앞으로 권고, PM은 이미지 전면 조정을 제외했다. 상단 텍스트만 먼저 옮기고 이미지 크기 전면 변경은 보류한다. 없는 응답을 잘못 읽는 문제를 먼저 해결하면서 범위를 제한한다.
4. **단순 표시 수정 vs 입력 경계 보강:** 메인은 21자리 검증을 별도 선택 안건으로 둘 수도 있다고 검토했다. QA·Architect는 실제 선택 근거를 추가하는 입구에서 정확한 20자리 조건을 요구했다. 최종적으로 **P2의 명시적 입력 표시 조건**에 포함했다. 기존 산식·질문·저장을 건드리지 않고 잘못 읽은 응답을 개인 근거로 인용하지 않도록 한다. 과거 비정상 링크의 동작 변경을 1절에 공개했다.
5. **그림 보존 vs 상승 그래프 우려:** PTRC 그림과 새 카피의 실제 사용자 해석은 미확인이다. 그림만으로 성과 보장이라 단정할 수 없으므로 기본안은 자산 유지, 특정 그래프 편집은 S2로 분리한다.

통합 순서는 **제품 핵심 원칙 → MVP 범위 → 구현 복잡도**다. 이번에는 새 기능보다 현재 결과의 정합성과 근거 표시를 닫는다.

## 8. 유지할 장점과 상태 분류

### 유지할 장점

- 랜딩의 20문항·로그인 불필요·시작 CTA, 한 문항·두 큰 선택지·자동 진행·이전 이동.
- 타입 코드로 다시 여는 결과와 코드 전용 공유. 응답 없는 화면에 저장된 답변을 합치지 않는 현재 구조.
- 네 축을 말로 풀어 주는 구조, 타입에 우열이 없다는 안내.
- 개미의 통일된 외형·색·소품·가벼운 별칭. 이름과 실제 해석을 혼동하지 않는 범위에서 보존.
- 4축 가이드의 일상 사례, 3:2·5:0 설명, 판단 기록 가이드의 완성 예시.
- 참고용·비진단 안내와 실제 금융상품·매매 행동을 제안하지 않는 원칙.

| 구분 | 이번 기준의 상태 |
|---|---|
| **완료** | 기존 진단·관찰 기록 확인, 핵심 화면 재확인, 보조 코드 검토, 여섯 역할 검토와 수정 승인안 작성. 제품 개선 구현 완료를 뜻하지 않음 |

**기존 URL 영향:** answers는 문항 배열 위치의 0/1이고 설문 버전 정보가 없다. 순서·선택지 위치·의미·매핑을 바꾸면 같은 예전 URL이 다른 선택지 또는 다른 코드로 해석될 수 있다. 코드가 달라지면 현재 판정은 응답 모드 대신 코드의 기본 설명으로 내려갈 수 있다. 코드 전용 링크는 계속 열려도 그 코드의 설명 체계가 바뀔 수 있다.

**별도 승인 전에 필요한 산출물:** 문항별 같은 상황의 두 행동 대비안, 각 문항 의도·매핑 근거, 예전 질문 버전/URL 해석 보존 정책, 기존 응답 결과 비교, 가이드·동점 규칙 영향 검토. Type System·Brand/Copy·Technical Architect·QA가 함께 검토한다. 이번 문서에는 점수·문항 수정 승인 요청을 포함하지 않는다.

## 10. QA 별도 정리

### 오해 가능성

- 선호 선택이 투자 능력·시장 감지·반응 속도·정확한 투자 시점 평가로 읽힐 수 있음.
- D/C 하나가 다른데 탐색 폭·고집·추진력까지 다르다고 읽힐 수 있음.
- 공유의 끝점·중간점·빈 척도에서 실제 응답 분포를 추측할 수 있음.
- 3:2의 반대 응답이 설명에서 사라지거나, 5:0을 항상 같은 성격으로 읽을 수 있음.
- 유효 answers URL을 여는 방문자를 실제 응답자로 인증한 것처럼 읽힐 수 있음.
- 타입 설명의 가상 장면을 개인이 고른 답변으로 혼동할 수 있음. 두 영역의 이름과 안내를 구분해야 함.
- 원문 질문의 복수 단서는 남아 있음. 실제 근거를 보여주는 것이 문항 타당성 증명은 아님.

### 금지 표현

- 종목·포트폴리오·맞춤 투자 추천, 수익·위험 회피 보장, 매수·매도 시그널처럼 행동을 제안하는 표현.
- 미측정 순위·능력: “가장 민감”, “남들보다 빠름”, “기회를 놓치지 않음”, “속도에 강함”, “균형이 좋음”, “추진력이 강함”.
- 횟수의 잘못된 변환: “성향 강도 60%”, “정확도 100%”, “준비 능력 60점”, “우수 타입”.
- 존재하지 않는 근거: 공유 결과의 개인 답변 인용, 5:0의 반대 선택, 숨은 동기·감정·실제 행동을 만들어 넣기.
- 질문형으로 바꾼 결함 단정: “왜 항상 충동적으로 행동하나요?” 등.

현재 관찰에서 실제 종목 추천·매매 지시가 있었다고 판정하는 것은 아니다. 제공하지 않는다는 안내에 등장하는 금지 개념과, 실제로 남은 능력 암시 문구를 구별한다. ‘타이밍’ 단어 자체를 금지하는 규칙도 아니다.

### 수동 검증 항목

6절의 시나리오를 실제 브라우저에서 수행하고, 특히 다음 세 비교를 검수한다.

1. **한 글자 비교:** 표의 같은 장면에서 달라진 축의 뜻만 설명되는가. 캐릭터·제목 때문에 성과 우열을 추가 해석하게 하는 문구가 남는가.
2. **3:2 / 5:0 / 코드 전용:** 무엇이 같고, 어떤 응답 정보가 다르며, 무엇은 아예 없는지 결과만 보고 구별할 수 있는가.
3. **원문 연결:** 표시된 질문·고른 답변·반영 글자가 URL 선택과 맞는가. 전체 5개 중 예시임을 알 수 있는가.

가능하면 실제 첫 방문자에게 자신의 말로 설명하도록 요청하고 어려워한 표현을 기록한다. 이것은 향후 확인 방법이며 수행된 사용자 연구 결과가 아니다. 임의의 참여 인원·정량 통과율·글 수·방문자 수를 승인 조건으로 두지 않는다.
