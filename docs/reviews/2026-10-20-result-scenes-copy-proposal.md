# 결과 장면 비교 검토와 교체 원고

작성일: 2026-10-20 KST. **현재 상태: 사용자 승인 후 적용·검증 및 운영 반영 완료.** 사용자의 ‘이 원고대로 결과 장면에 적용하고 검증까지 해줘’ 요청에 따라 구현했고, 이어 ‘검증한 변경을 운영에 반영하고 실제 사이트에서도 확인해줘’라는 별도 승인을 받아 배포했다. [로컬 적용·검증](2026-10-20-result-scenes-verification.md)과 [운영 반영·검증](2026-10-20-result-scenes-production-verification.md)에 실행 결과를 남겼다. 아래 원고와 편집 검토는 승인 기준으로 보존한다.

사용자는 [개선 후 재심사 반려 검토](2026-10-20-adsense-rejection-followup.md)의 ‘한 글자만 다른 네 비교쌍을 검토하고 부족한 기존 장면·해설부터 보완’하자는 제안에 동의했다. 이번 산출물은 그 비교와 실제 교체 원고다. 이번 동의를 배포나 AdSense 재제출 요청으로 확대하지 않는다.

원고 검토 기준은 `.worktrees/approved-experience`의 `572c8e6`이다. 루트의 `4321fe9`를 현재 제품으로 보고 원고를 만들지 않았다. 질문·축 정의·본문·공통 예시 안내·두 가이드를 함께 확인했다. 후속 운영 반영 커밋은 `22341be`다.

## 목표와 성공 기준

목표는 타입 이름을 읽은 사람이 자신의 선택에서 무엇을 돌아볼지 구체적인 장면을 떠올릴 수 있게 하는 것이다. 사용자 요청은 네 비교쌍의 검토이며, 기존 두 장면을 구체화하는 방식은 이번 검토의 제안이다.

- 같은 상황에서 한 글자만 다른 결과가 무엇에 먼저 주목하는지 드러난다.
- 한 축의 차이를 설명하려고 다른 축이나 새로운 성격 특성을 바꾸지 않는다.
- 기존 장면 두 개 안에서 상황과 관찰 대상을 제시한다. 별도 질문이나 설명 섹션은 추가하지 않는다.
- 실제 답변 인용과 타입 공통 예시의 구분, 투자 추천 비제공 원칙을 유지한다.

이 원고가 사용자 효용이나 AdSense 승인 가능성을 검증한 결과는 아니다. 기존의 조합 구조와 일부 공통 문장은 남는다. 이번 편집의 목표는 페이지 수나 고유 문장 수가 아니라 구체적인 이해다.

## 네 비교쌍에서 확인한 점

현재 원문은 [타입 데이터](../../src/data/type-profiles.ts), 해석 기준은 [축 정의](../../src/data/axes.ts)와 [질문](../../src/data/questions.ts)이다.

| ALRD / PLRD | 출발 전에 순서 정리 / 현장에서 순서 결정 | 준비 시점 외에 살펴보는 대상이 추상적 | 같은 전시·산책과 비라는 조건에서 미리 정리한 대안 / 현장에서 살펴본 장소를 구분. L의 하루 흐름은 동일 |

| ALRD / ALRC | 항목별 기능 설명 / 전체 사용 장면 | 축 정의를 다시 읽는 수준에 머묾 | 같은 검색 기능을 자료 종류·결과 표시의 항목으로 이해 / 저장→검색→다시 열기의 과정으로 이해 |

첫 장면은 A/P와 L/T, 두 번째 장면은 R/I와 D/C를 설명한다. 첫 장면에서 D/C의 합리성 차이를 만들거나 두 번째 장면에서 A/P의 실행 속도를 추가하지 않는다.

## 제안하는 적용 범위

**기존 `scenes` 두 개를 아래 8개 문안의 조합으로 교체한다.** 네 비교쌍은 검토 표본이며 같은 기준을 16개 결과에 적용한다. 5개 표본 타입만 바꾸면 같은 축 조합을 가진 나머지 타입과 설명이 달라지므로 모든 타입의 매핑을 함께 명시한다.

| 검토한 방식 | 판단 |
|---|---|
| 기존 장면 두 개 교체 | 채택. 현재 데이터와 화면에서 상황·관찰 대상을 구체화할 수 있음 |
| 장면 뒤에 별도 해설·질문 추가 | 제외. 네 돌아볼 질문과 중복되고 공유까지 읽을 분량이 늘어남 |
| 16개 전부 다른 사건 또는 새 비교 UI | 제외. 축 의미가 달라지거나 근거 없는 특성을 더할 위험, 구현 범위 증가 |

제품 적용 위치는 최신 worktree의 `src/data/type-profiles.ts` 내 `scenes`다. `TypeProfile.scenes`의 `[string, string]` 구조와 `ResultPageContent`의 기존 렌더링을 이용한다. 변경 전후 점검은 scenes 외 제품 필드가 같은지도 확인한다.

타입명·headline·description·reflections·shareText, 네 축과 20개 질문·집계, 개인/공유 모드, URL·메타·이미지·광고는 이 원고의 변경 대상이 아니다. 가이드에는 이미 집계 사례와 실제 장면을 돌아보는 방법이 있으므로 같은 설명을 다시 추가하지 않는다.

## 장면 1 — 나들이: 준비 방식과 시간 시야

모든 문안은 같은 전시·산책 목적과 도착 뒤 비가 내리는 조건을 사용한다. P도 나들이의 목적은 가질 수 있으며, 갈 곳의 순서를 현장에서 정하는 것으로 구분한다. L도 변화에 대응하고 T도 미리 준비할 수 있다. 무엇을 잘하는지나 최종 선택을 예측하지 않는다.

### SCENE-AL

> 전시를 보고 산책하려던 날, 도착하니 비가 내리는 장면이에요. 출발 전에 정리해둔 방문 순서와 실내 대안을 떠올려요. 바뀐 동선에서도 전시를 보고 쉬어가려던 하루의 흐름을 어떻게 이어갈지 살펴봐요.

### SCENE-AT

> 전시를 보고 산책하려던 날, 도착하니 비가 내리는 장면이에요. 출발 전에 정리해둔 방문 순서와 실내 대안을 떠올려요. 지금 비를 피할 장소와 바로 바꿀 이동 순서를 살펴봐요.

### SCENE-PL

> 전시를 보고 산책하려던 날, 도착하니 비가 내리는 장면이에요. 도착해서 주변의 실내 장소를 살펴보며 갈 곳의 순서를 정해봐요. 바뀐 동선에서도 전시를 보고 쉬어가려던 하루의 흐름을 어떻게 이어갈지 살펴봐요.

### SCENE-PT

## 장면 2 — 메모 앱: 관심의 출발점과 납득 방식

모든 문안은 사진 속 글자 검색 기능이 있다는 같은 가상 메모 앱을 다룬다. R/I는 먼저 떠올린 기준과 새 정보, D/C는 같은 기능을 이해하는 설명 방식만 달라진다. R이 새 기능을 거부하거나 I가 곧바로 채택한다는 결론은 없다. C도 구체적인 기능을 살펴본다.

### SCENE-RD

> 사진 속 글자도 검색된다는 메모 앱을 살펴보는 장면이에요. 예전부터 중요하게 보던 ‘저장한 내용을 다시 찾기 쉬운가’를 먼저 떠올려요. 검색할 수 있는 자료의 종류와 결과가 표시되는 방식을 항목별로 보며 그 쓰임을 이해해요.

### SCENE-RC

> 사진 속 글자도 검색된다는 메모 앱을 살펴보는 장면이에요. 예전부터 중요하게 보던 ‘저장한 내용을 다시 찾기 쉬운가’를 먼저 떠올려요. 찍어둔 안내문을 저장하고, 나중에 단어로 검색해 다시 여는 장면이 그려지면 그 쓰임을 이해해요.

### SCENE-ID

> 사진 속 글자도 검색된다는 메모 앱을 살펴보는 장면이에요. ‘사진에 있는 글자까지 찾을 수 있네’라는 새 정보에 먼저 눈길이 가요. 검색할 수 있는 자료의 종류와 결과가 표시되는 방식을 항목별로 보며 그 쓰임을 이해해요.

### SCENE-IC

> 사진 속 글자도 검색된다는 메모 앱을 살펴보는 장면이에요. ‘사진에 있는 글자까지 찾을 수 있네’라는 새 정보에 먼저 눈길이 가요. 찍어둔 안내문을 저장하고, 나중에 단어로 검색해 다시 여는 장면이 그려지면 그 쓰임을 이해해요.

> 아래는 같은 타입에 공통으로 제공되는 설명이에요. 장면은 타입의 뜻을 풀어 쓴 예시이며, 실제 선택 기록은 아니에요.

## 역할별 검토와 통합 이유

| 역할 | 초기 검토 | 메인 반영 |
|---|---|---|
| Type System | 같은 조건에서 초점 차이만 보여야 함. AL/AT의 변수 유무 차이 제거, RI/DC에서 같은 기능 유지 | 나들이에 같은 비를 적용. 앱은 사진 검색 기능과 설명 대상을 고정 |
| Brand/Copy | 8개 구체 장면으로 모든 타입에 동일 편집 기준 적용. 상황·관찰 대상이 드러나는 해요체 | 8개 문안과 16개 매핑 완성. 최종 선택이나 능력 평가 없이 장면으로 표현 |
| UX/IA | 기존 두 장면 교체. 새 섹션·비교 UI는 범위와 읽기 부담 증가 | 데이터 구조·순서 유지. 짧은 문장 세 개로 분리하고 기존 질문으로 연결 |

조정한 쟁점은 장면마다 질문을 덧붙일지와 장면 길이다. Brand 초안의 추가 돌아보기 질문은 기존 네 질문과 겹쳐 제외했다. UX의 짧은 두 문장 제안은 긴 복문을 피하도록 세 개의 짧은 문장으로 조정했다. 제품 원칙과 모바일 읽기 부담을 우선했다.

최종 후보 재검토에서 Type System은 네 비교쌍의 축 정합성과 16개 매핑에 수정이 필요 없다고 판단했다. Brand/Copy는 RC·IC 끝 문장의 추상적 표현이 겹치는 부분을 ‘다시 여는 장면이 그려지면 그 쓰임을 이해해요’로 다듬도록 권고했으며 두 곳에 동일 반영했다. UX/IA는 세 문장 구성과 기존 구조 적용이 적절하다고 판단했고, 실제 모바일 가독성은 적용 후 검증으로 남겼다. 원고 검토 단계의 역할 간 미해결 충돌은 없다.

## 적용 후 확인할 사항

1. 16개 타입의 장면이 모두 2개이며 적용표와 일치한다. 네 비교쌍에서 바뀐 축에 해당하는 문장만 달라지는지 확인한다.
2. 개인 응답·코드 전용·잘못된 answers 세 모드에서 공통 예시 안내와 실제 응답 사례가 구분된다. 새 원고가 개인 답변을 관찰한 기록처럼 보이면 문구를 조정한다.
3. 360px 모바일과 데스크톱에서 장면 두 개와 기존 돌아볼 질문을 읽고 공유까지 이동한다. 가로 넘침·글자 잘림과 문단 길이를 확인한다. 200% 확대와 실제 휴대폰은 별도 실행 결과가 있을 때만 완료로 기록한다.
4. 기존 집계·결과 매핑 검사를 실행하고 린트·빌드를 확인한다. 문구를 그대로 복제하는 새 테스트나 글자 수를 품질로 판정하는 테스트는 만들지 않는다.
5. 제품 적용 시 README의 결과 장면 설명과 구현 범위를 확인한다. AdSense 계정 작업은 별도 요청 범위다.

## 남는 한계와 이번 검증

- 조합형 결과와 공통 문장은 남는다. 문장을 길게 쓰는 것만으로 반복 콘텐츠 문제가 해결됐다고 주장하지 않는다.
- 심리검사 타당성, 실제 사용자 효용·재방문, AdSense 반려 원인은 이번 원고 검토로 검증되지 않는다.
- 공유 화면의 예시를 개인 행동 예측으로 읽거나 A/P·L/T·R/I·D/C를 능력 우열로 읽을 가능성을 검토했다. 투자 추천·수익 보장·검증된 진단 표현을 추가하지 않는다.
